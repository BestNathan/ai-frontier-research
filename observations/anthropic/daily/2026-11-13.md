## Engineering questions and comparison

Three distinct control-plane concerns converge in these sources: (1) persistence of knowledge and execution identity across sessions, (2) coordination and isolation across large agent fleets, and (3) verifying remote model execution and tool side effects. Separating these concerns helps avoid treating model capability announcements as platform architecture disclosures.

| Infrastructure problem | Evidence source | Candidate mechanism | Open validation question |
| --- | --- | --- | --- |
| Trustworthy session-independent knowledge | [Agent memory](https://www.anthropic.com/research/components-of-agent-memory) | Logs, mutable notes, consolidated representations, offline reconciliation | How can stale or false notes be detected before reuse? |
| Long-session transport overhead | [Message threads](https://claude.com/resources/articles/message-threads) | Short-lived provider-side thread state, incremental client messages | How does recovery behave after expiration or lost acknowledgments? |
| Large-fleet coordination and security | [1,000-agent experiment](https://claude.dev/blog/safely-scaling-multi-agent-teams-with-fable-5-2/) | Isolated VMs, guarded gateway, shared transactional state and Git branches | Which coordination and contention costs survive domain changes? |
| Data-plane and control-plane locality | [Self-hosted Managed Agents](https://claude.com/resources/articles/self-hosted-claude-managed-agents) | Separately hosted harness, sandboxes, credentials and session history | Which recovery and isolation guarantees are independently testable? |
| Proof of model identity and correct execution | [FlashProve](https://www.anthropic.com/research/provable-inference) | zkSNARKs and audited verifier statements | Does verification cost permit any practical production workload? |

## 1. Durable memory is a learning and correction lifecycle

- **Primary article:** [The components of agent memory](https://www.anthropic.com/research/components-of-agent-memory)
- **Publication:** 2026-11-06, **observed:** 2026-11-13
- **Source class:** First-party Engineering article; reported evaluations, not independently replicated
- **Related domains:** [Context and retrieval](../../../domains/context-and-retrieval.md), [Durable execution](../../../domains/durable-execution.md), [Evaluation](../../../domains/evaluation.md)

**Engineering problem:** A long-lived agent needs to carry useful knowledge across independently restarted sessions, but cannot know the future usefulness of an observation when first recording it. Persisting everything creates search cost and stale-state contamination.

**Verified (publisher-reported):**

- The article distinguishes session logs/transcripts, agent-written memory notes, richer representations such as wikis, and injected next-session context. Offline **dreaming** uses historical evidence to consolidate or correct stored notes.
- In a CL-Bench database task, some models used a persistent memory directory to test and record rules, while weaker models wrote untested guesses. The article reports, for example, Opus 5.5 mean reward **0.655 without versus 0.838 with memory** on that task, under its evaluation setup.
- A separate Pokémon task compared agents with sharply different memory sizes and outcomes; these are illustrative evaluations, not a universal compression or retrieval benchmark. Prescriptive memory rules could reduce gains for stronger models.

**Inferred:** A useful memory platform should separate an append-only evidence log from mutable, confidence-labelled knowledge materializations. It should support source provenance, TTL/invalidations, retrieval ranking and scheduled reconciliation; a compact note is a derived view, not an authoritative event.

**Alternatives:** Full transcript replay (simple but expensive), on-demand semantic retrieval (freshness and ranking risk), extracted memory notes (better density but verification burden), and periodically reconciled knowledge representations.

**Unknown:** Exact internal implementation, scheduling, source consistency, access controls and contamination rate in production.

**Hypothesis / experiment:** Fix a multi-session engineering corpus with intentionally outdated and contradictory instructions. Compare stateless replay, raw retrieval, agent-written notes and offline reconciliation on task success, stale-fact acceptance, recall@K, token cost, human correction minutes and p95 retrieval latency. Require traceable provenance for promoted rules.

## 2. Message threads optimize request transport, not token reasoning

- **Primary article:** [Make long-running agents faster with message threads](https://claude.com/resources/articles/message-threads)
- **Publication:** 2026-11-02, **observed:** 2026-11-13
- **Source class:** First-party Claude Platform feature disclosure (public beta)
- **Related domains:** [Durable execution](../../../domains/durable-execution.md), [Context and retrieval](../../../domains/context-and-retrieval.md)

**Engineering problem:** Resending increasingly long messages and tool results for each agent step adds transport and preparation latency even when the model still needs the same effective context.

**Verified (publisher-reported):**

- Clients provide initial history, then subsequent requests transmit only new messages and the previous response ID through a `thread` parameter.
- Anthropic reports approximately **35% lower median time-to-first-token** for requests with 500k–1M tokens in applicable Claude Code use; this is not an independently reproduced result.
- Thread state is encrypted in provider memory and expires after **five minutes of inactivity**, after which the client must resend full context. The article explicitly says total model token usage is unchanged.

**Inferred:** Treat thread state as an opportunistic server-side transport cache, not a durable session source of truth. The client/orchestrator must retain enough authoritative conversation history to rebuild a session and handle expiry, retries, reordering and ambiguous tool acknowledgments.

**Alternatives:** Full-history requests (stateless and robust but bandwidth-heavy), client compaction (changes effective context), long-lived provider sessions (retention/cost/ownership constraints), short-lived incremental threads (cache-miss recovery burden).

**Unknown:** Reordering semantics, cross-region failover, concurrent branch support, exact billing of cached transport and guarantees under gateway retries.

**Hypothesis / experiment:** Replay fixed 100/500/1,000-step agent transcripts under stable and flaky networking with five-minute pauses. Compare TTFT p50/p95, network bytes, total billed tokens, cold-resume correctness, duplicate tool effects and recoverable session identity.

## 3. The 1,000-agent study separates execution sandboxes from shared coordination

- **Primary article:** [Safely scaling multi-agent teams with Claude Fable 5.2](https://claude.dev/blog/safely-scaling-multi-agent-teams-with-fable-5-2/)
- **Publication:** 2026-11-09, **observed:** 2026-11-13
- **Source class:** First-party experiment, not a general-purpose production deployment
- **Related domains:** [Orchestration](../../../domains/orchestration.md), [Security](../../../domains/security.md), [Source control](../../../domains/source-control.md), [Verification](../../../domains/verification.md)

**Engineering problem:** Agent count grows faster than single-host resource capacity and shared-state coordination, while autonomous shell/file actions can cross unsafe boundaries.

**Verified (publisher-reported):**

- Anthropic reports a **1,000-agent** run that completed its Lean formalization task in **28.7 hours**. Agents ran in separate lightweight VMs, each with a shell/editor, Lean toolchain, isolated Git branch and shared PostgreSQL; one lead directed helpers.
- A prior shared-machine approach reached serious resource limits at around **100 agents**. The distributed experiment gave each sandbox no general network access; one gateway handled model, Git and SQL requests.
- The gateway assigned agent identity *outside* the sandbox. SQL access used an unprivileged role, individual statements had a five-second timeout and writes were bounded. A classifier pre-checked shell/file operations and an offline monitor reviewed activity.
- A separate merge job moved branch changes into main; Lean checked formal proof artifacts. The agents evolved their own task/notes coordination tables.

**Inferred:** The scalable boundary is an isolated execution data plane plus shared, transactional coordination and revision-pinned evidence. A SQL database is a flexible control-plane substrate, but the workload may be dominated by contention, dead agents holding claims, large fan-out and stale progress signals.

**Alternatives:** Leader-allocated task queues with leases, shared append logs with materialized task state, transactional SQL claims, or decentralized coordination. Shared writable working directories would simplify communication but increase interference.

**Unknown:** Full cost including gateway/DB/VM overhead, throughput scaling across different task graphs, conflict rate, false-positive guard decisions, repeatability and the exact recovery model for failed agents.

**Hypothesis / experiment:** Reproduce a 10/100/1,000-agent task DAG at a fixed source SHA; inject agent crashes, duplicated SQL claims, Git conflicts, lost gateway replies and resource saturation. Measure successful verified tasks per dollar, p95 work-start lag, orphan task recovery, DB hotspots, safety escapes and merge conflict/retry rates.

## 4. Self-hosted Managed Agents clarify ownership and trust boundaries

- **Primary article:** [Operate Claude Managed Agents inside your security perimeter](https://claude.com/resources/articles/self-hosted-claude-managed-agents)
- **Publication:** 2026-11-12, **observed:** 2026-11-13
- **Source class:** First-party product/architecture disclosure; private beta, not source audit
- **Related domains:** [Durable execution](../../../domains/durable-execution.md), [Security](../../../domains/security.md), [Orchestration](../../../domains/orchestration.md)

**Engineering problem:** Long-running coding agents need access to sensitive internal code, credentials and services. Local-only sandboxes do not by themselves give an organization control of the agent server, session history and credential lifecycle.

**Verified (publisher-reported):**

- The private beta runs the Managed Agents **server, database, harness, sandbox workers, credentials and session history** in the customer's cloud or on-premises environment. Model calls may route to Anthropic, supported cloud providers or a chosen gateway.
- The design separates the **agent loop / session log** from the sandbox executing shell/file tools. Session history remains outside an ephemeral sandbox as an event log; tools can be started when needed.
- Credentials are intended to remain outside agent execution, injected through a proxy for supported external tool/API calls. Egress allowlists, sandbox boundaries and OpenTelemetry export are discussed as architectural safeguards.
- The post presents the same core APIs across managed-hosted and self-hosted forms, but does not publish a complete implementation specification.

**Inferred:** The meaningful trust boundary is not merely "sandbox hosted locally" but **control-plane authority**, data-plane authority, secret-injection points and recoverable execution state. An independently operated gateway and audit trail may simplify vendor-neutral governance.

**Alternatives:** Provider-managed full stack, provider control plane + customer-hosted sandboxes, self-hosted full control plane, or a lightweight internal runtime with independently managed sandbox fleet.

**Unknown:** Deployment topology, upgrade and version compatibility model, database isolation/recovery, tenant boundaries and the complete failure-handling contract.

**Hypothesis / experiment:** Compare two hosting topologies with the same tool workload. Test worker restarts, expired credentials, lost model responses, partial network isolation and rotated model routes; measure secret exposure, successful run recovery, audit completeness, operational cost and update-induced regressions.

## 5. FlashProve expands the frontier of inference attestation

- **Primary article:** [Progress on provable inference for large language models](https://www.anthropic.com/research/provable-inference)
- **Publication:** 2026-11-02, **observed:** 2026-11-13
- **Source class:** First-party Frontier Red Team research and released artifacts
- **Related domains:** [Security](../../../domains/security.md), [Verification](../../../domains/verification.md), [Evaluation](../../../domains/evaluation.md)

**Engineering problem:** A remote model API user ordinarily cannot cryptographically verify that the requested model and weights produced a particular response.

**Verified (publisher-reported):**

- FlashProve uses zero-knowledge proof techniques to attest model inference without revealing weights. Anthropic describes a **400B-parameter mixture-of-experts model (Llama 4 Maverick)**, about **110 proof tokens per second** on one H100 under specified quantization/arithmetic conditions, and approximately **19 MB proof size** for a 1,024-token request.
- Anthropic estimates the proof-generation workload at **70–95x** normal vLLM inference GPU time for this setup. These numbers are not representative production overheads across models.
- The team published a technical report, executable prover/verifiers and Lean statements/proofs for review, while explicitly treating the project as intermediate research.

**Inferred:** Attestation may eventually strengthen AI service identity and auditability, but high prover overhead is currently a major economic barrier. Formal verifier correctness, proof/weights binding and key-management assumptions are separate from model output quality.

**Alternatives:** Trust in provider routing plus logs, enclave-backed execution attestation, sampled independent reruns (not full integrity assurance), and cryptographic proof systems with different prover/verifier economics.

**Unknown:** Performance on production transformer families and dynamic routing, trusted model-commitment distribution, continuous batching overhead, and end-to-end operational cost.

**Hypothesis / experiment:** Pin the released code to a fixed commit, verify source proof results at reproducible settings, and compare proof generation/verifier p95, proof size, memory footprint and GPU-dollar overhead across sequence lengths, quantization settings and model sizes. Record exactly which statement the proof establishes.

## Cross-cutting technical conclusions

- **Verified (publisher-reported):** These sources expose distinct patterns: memory consolidation, short-lived transport state, coordinated isolated execution, self-hosted control-plane authority and cryptographic model attestation.
- **Inferred:** Keep **authoritative state**, **derived context**, **ephemeral transport caches**, **tool-side effects**, **shared coordination** and **verification evidence** as separate abstractions with explicit provenance.
- **Hypothesis:** This separation improves failure recovery and auditability under fleet-level concurrency without requiring every agent task to rebuild context or revalidate every artifact.
- **Unknown:** Whether any of Anthropic's private implementations share backends, hidden schedulers or storage mechanisms. No source here supports treating them as one integrated internal architecture.
