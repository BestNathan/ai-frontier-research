# Durable Agent Control Planes, Safety Evaluation, and Proof-Driven Verification

**Observed:** 2026-11-14  
**Publication window:** 2026-10-08–2026-11-13 (new November 13 publications and selected previously unrecorded technical backfill)  
**Evidence class:** First-party disclosures and methodology; no independent replication or code audit performed.  
**Discovery:** [Claude Resources](https://claude.com/resources), [Articles](https://claude.com/resources/articles), [Anthropic Engineering](https://www.anthropic.com/engineering), [Anthropic Research](https://www.anthropic.com/research), [Claude Developer Blog](https://claude.dev/).

## Engineering problem and invariants

An unattended agent platform needs durable event intake, bounded concurrent execution, explicit permissions, crash-safe delivery, and a way to prove that its outputs and safeguards satisfy the intended specification. More elaborate multi-agent topology is not automatically more correct. Invariants to preserve across implementations:

1. **Durability:** accepted events and user-visible outcomes survive process failure; source failures cannot silently advance a checkpoint.
2. **Attribution:** each side effect is linked to an authorized actor, task, input revision, tool call and result.
3. **Concurrency:** concurrent triggers cannot silently overwrite the same mutable session or deliver the same effect twice.
4. **Safety:** evaluation environments and tool credentials are scoped; measured safety is not equated with mere refusal.
5. **Verification:** every claimed guarantee states its precise specification, trusted computing base, and excluded execution conditions.

## 1. Always-on agents: event-driven execution instead of immortal processes

- **Original:** [Building always-on agents](https://claude.com/resources/articles/building-always-on-agents)
- **Published:** 2026-11-13; **observed:** 2026-11-14
- **Classification:** First-party architecture guide, not a published production benchmark.
- **Domains:** [Durable execution](../../../domains/durable-execution.md), [Orchestration](../../../domains/orchestration.md), [Security](../../../domains/security.md), [Delivery](../../../domains/delivery.md)

**Engineering question:** How can an agent behave continuously without holding an always-running model process, while preserving event correctness and authorization across short-lived sessions?

**Verified (publisher-reported):** The guide defines five surrounding primitives: **event inbox, timers, memory, permissions, outbox**. An inbox stores accepted events durably with source-specific deduplication; an HTTP handler acknowledges promptly and a worker starts a session or resumes one. A timer scheduler enqueues due events rather than directly invoking an agent. One active worker per inbox is suggested to avoid conflicting runs, and pending events can be batched. Memory is separate durable state; permissions include credential proxies and deferred approvals; an outbox plus dispatcher supports recoverable delivery. The model executes in short runs and is otherwise asleep. The article describes a design pattern, not exact database isolation levels, transaction boundaries or measured reliability.

**Inferred:** Treat the inbox as authoritative admission state and the outbox as authoritative delivery intent. The critical transaction is not simply event acceptance: run progress, external side effects and delivery receipts need independently reconcilable identifiers. A per-user single worker simplifies serialization but may become a throughput bottleneck. Event deduplication alone cannot make non-idempotent external tools exactly-once.

**Alternatives:** Direct webhook-to-agent invocation (minimal latency, weak recovery); durable queue plus stateless workers (scalable but needs ordering and leases); database-backed inbox and outbox (transactional consistency at operational cost); durable execution engines (workflow history and replay, vendor/runtime coupling).

**Unknown:** Atomicity of timer firing versus inbox insertion, worker lease expiry, replay order, session ownership transfer, deferred-call authentication, and delivery acknowledgement semantics in any particular deployment.

**Hypothesis / experiment:** Implement a reference Postgres inbox/outbox and an alternative queue-backed design at pinned source revisions. Inject crashes (before/after event ACK, tool call, state commit, outbox send), duplicate webhooks, network partitions and simultaneous triggers. Measure lost/duplicated effects, recovery p95, lease contention, throughput per user and cost per correctly delivered task. Explicitly document at-least-once delivery and idempotency-key coverage.

## 2. Safety evaluation is an experimental measurement problem

- **Original:** [Building strong safety evaluations](https://www.anthropic.com/research/building-strong-safety-evaluations)
- **Published:** 2026-11-13; **observed:** 2026-11-14
- **Classification:** First-party engineering/evaluation methodology; recommendations, not an independent validation of all system-card measurements.
- **Domains:** [Evaluation](../../../domains/evaluation.md), [Security](../../../domains/security.md), [Verification](../../../domains/verification.md)

**Engineering question:** What evidence supports a safety gate when the chosen metric may reward refusal, overfit to a benchmark, or miss dangerous multi-turn behavior?

**Verified (publisher-reported):** Anthropic distinguishes observational comparisons from causal intervention tests; recommends matching the design to the question, measuring the intended construct, domain-expert rubrics, benign/harmful paired tasks, and multi-turn appropriate-response grading (one bad turn fails the conversation). It highlights pre-registration, statistical reporting, reproducibility and disclosure of limitations. Safety evals may need sandboxes with no internet access and real-time monitoring; the article reports Anthropic temporarily stopped many internet-enabled evaluations after incidents and hardened its environments.

**Inferred:** A safety gate should be a versioned evidence artifact, not a single aggregate refusal score. An eval registry should bind the model revision, harness, policy, grader, dataset provenance, allowed tools, environment fingerprint and confidence intervals. Separate under-refusal, over-refusal, harmful tool effects and multi-turn failure, and preserve both false-negative and false-positive costs.

**Alternatives:** Static refusal-rate tests (cheap but weak construct validity); multi-turn human-rubric grading (richer but costly); model-as-judge with calibration (scalable but correlated error); sandboxed end-to-end behavioral tests (realistic but harder to contain and reproduce).

**Unknown:** Exact internal sampling, grader calibration, inter-rater agreement, preregistration enforcement, test-set leakage and deployment gate thresholds. No numerical causal effect should be inferred from the methodology alone.

**Hypothesis / experiment:** Fix a stratified set of authorized/unauthorized tool tasks with single-turn and multi-turn variants. Compare refusal-only scoring against expert-defined appropriate-action rubrics under blinded human adjudication. Report false acceptance/rejection, confidence intervals, grader agreement, variance over repeated runs, containment incidents and per-eval cost. Pre-register exclusion and analysis rules.

## 3. AI-assisted formal verification moves the trusted boundary to the proof checker and semantics

- **Original:** [LLMs are making formal software verification feasible at a much larger scale](https://www.anthropic.com/research/formal-verification)
- **Published:** 2026-10-22; **observed:** 2026-11-14 (technical backfill)
- **Classification:** First-party Frontier Red Team and Theorem experiment; author-reported results.
- **Domains:** [Verification](../../../domains/verification.md), [Security](../../../domains/security.md), [Evaluation](../../../domains/evaluation.md)

**Engineering question:** Can an LLM convert fuzz entry points into machine-checkable guarantees over compiled code, rather than merely generate more test inputs?

**Verified (publisher-reported):** The pipeline compiles library fuzz harnesses to **RISC-V**, combines executable instructions with formal RISC-V/Linux semantics and a no-crash property for inputs **under 64 MB**, and uses Claude to generate **Rocq** proofs checked by the Rocq kernel. Anthropic reports proofs for **239 entry points across 123 OSS-Fuzz libraries**, approximately **180 million lines of Rocq** in total, and a typical proof of around **600,000 lines** for a binary with a median **18,000 RISC-V instructions**. The guarantee is conditional on single-threaded, statically linked binaries, fixed memory budget, modeled Linux behavior and the trusted semantics/checker. Some programs were patched before a new specification was generated. Anthropic also reports that sharing reusable proof artifacts reduced token use by **17%** in a 36-task study; this is not a cross-project cost guarantee.

**Inferred:** The main benefit is a narrower trusted computing base and independently checkable proof artifact, not a blanket claim of bug-free software. A patch changes the executable and therefore the theorem target: proof provenance must bind the exact compiled artifact, compiler flags, source SHA, spec and checker version. Fuzz-test-derived properties cannot cover behavior outside the harness, unmodeled concurrency or incorrect environmental assumptions.

**Alternatives:** Continuous fuzzing (probabilistic discovery); symbolic execution/SMT (path explosion); source-level deductive verification (requires richer specifications); binary-level theorem proving (stronger artifact correspondence but substantial proof cost).

**Unknown:** Generalization to dynamically linked, multi-threaded, x86/ARM production services, complete proof generation cost and proof maintenance under frequent code changes.

**Hypothesis / experiment:** Pin a released proof repository SHA and independently replay its checker on a small set of unmodified binaries. Recompile with one controlled semantic change and confirm the old proof cannot be accepted for the new artifact. Compare proof time/token cost and incremental maintenance against fuzzing and targeted symbolic execution. Inspect the exact trusted statement before claiming a safety property.

## 4. Consolidating subagents: topology is an empirical choice

- **Original:** [Building agents: When to fold subagents into your main agent loop](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop)
- **Published:** 2026-10-22; **observed:** 2026-11-14 (technical backfill)
- **Classification:** First-party applied engineering guidance, not an independently controlled universal benchmark.
- **Domains:** [Orchestration](../../../domains/orchestration.md), [Context and retrieval](../../../domains/context-and-retrieval.md), [Evaluation](../../../domains/evaluation.md)

**Engineering question:** When do specialist agents improve isolation and parallelism, and when do nested loops merely lose context and increase latency?

**Verified (publisher-reported):** Anthropic describes consolidating tightly coupled specialist agents into a single open-ended tool loop with **progressively disclosed skills and tool search**. The main model plans, batches parallel tool calls, observes results and revises the plan; the harness retains hard budgets, write gates and validation. In one customer comparison, a single-loop design ran approximately **2x faster** than the multi-agent harness, with no claim that all workloads see this improvement. The article recommends preserving subagents for genuine parallelism, fresh-context isolation, difficult tool selection or conflicting instructions. It advocates end-to-end task-completion evals and reports a migration regression that only appeared on one of two runs.

**Inferred:** Subagent count should be an optimization variable, not an organizational chart. Move domain procedures to versioned skills, live operations to permission-checked tools, and hard invariants to the harness. Preserve separate agent contexts where they materially reduce context interference or enforce least privilege. A single context may improve fidelity but raise token, contention and privilege-coupling risks.

**Alternatives:** Single loop plus progressive disclosure; orchestrator-subagent with structured handoff; generator-verifier; independent parallel agent teams; specialized deterministic workflows.

**Unknown:** Dataset composition, customer workload distribution, model-version sensitivity, tail latency and error-rate tradeoffs of the quoted speed comparison.

**Hypothesis / experiment:** Build paired workflows at a fixed model/harness revision and tool schema. Compare one loop versus two-stage specialist handoffs versus parallel agents on task-completion accuracy, instruction-conflict rate, p50/p95 latency, tokens, dollar cost, permission failures and handoff information loss. Use repeated trials and a fixed end-to-end golden set; fail migration if a previously passing critical invariant regresses.

## 5. Reliable agent automations need durable checkpoints and delivery receipts

- **Original:** [Building effective agent automations](https://claude.dev/blog/building-effective-agent-automations/)
- **Published:** 2026-10-08; **observed:** 2026-11-14 (technical backfill)
- **Classification:** First-party reference-implementation walkthrough, not an audited production SLA.
- **Domains:** [Durable execution](../../../domains/durable-execution.md), [Security](../../../domains/security.md), [Delivery](../../../domains/delivery.md)

**Engineering question:** How can a recurring agent distinguish no new source data from source failure, avoid duplicate notifications, and safely resume after ambiguous delivery?

**Verified (publisher-reported):** Anthropic's example defines a source list, destination, versioned agent, schedule, memory stores and guardrails. Per-source bookmarks avoid gaps caused by fixed lookback windows. A failed read leaves the bookmark unchanged and is disclosed instead of misreported as a quiet day. Scoped credentials live in a vault outside the sandbox and are inserted by a proxy for permitted hosts. The delivery ledger is updated only after the destination acknowledges a successful send with a message identifier; ambiguous outcomes are recorded without moving checkpoints. The article supplies a reference configuration and code link, but no published end-to-end reliability statistics.

**Inferred:** A robust research collector should maintain separate **source observation watermark**, **article canonical URL ledger**, **GitHub PR/merge outcome**, and **user notification receipt**. A successful source read must not advance publication state if the GitHub write fails. A fixed calendar day is a reporting label, not a safe ingestion watermark.

**Alternatives:** Stateless daily scanning with repository-wide deduplication (simpler but expensive and coverage-sensitive); per-source checkpoints (efficient but must handle backfill); event-sourced ingestion with an outbox (strong auditability but greater complexity).

**Unknown:** Exactly-once guarantees of the sample under simultaneous deployments, destination API timeout and source clock skew.

**Hypothesis / experiment:** Run the same collector under forced 24-hour downtime, source 401/500, stale pagination, duplicate URLs, and an acknowledged GitHub write followed by lost response. Verify no missing canonical articles, no false quiet-day report and no duplicate PRs. Record source, PR and notification states independently.

## Synthesis and research priorities

**Verified (publisher-reported):** These sources respectively document a durable five-primitive agent control plane, evaluation design safeguards, binary-level proof generation, subagent consolidation patterns and reliable source-to-destination automations.

**Inferred:** Durable state, capability enforcement and verifiable outcomes should be separate layers. The strongest recurring invariant is **evidence must survive failures and be bound to the exact action/artifact it claims to validate**. The topology of model loops and the number of workers can change without weakening that invariant.

**Hypothesis:** A small control plane with a durable inbox/outbox, revision-pinned tool effects, per-source ingestion ledger and evidence-aware eval gates will yield fewer lost or duplicated operations than ad-hoc agent schedules, at acceptable operational overhead.

**Unknown:** Whether Anthropic uses these exact primitives internally across all products; no source here establishes a unified private implementation.
