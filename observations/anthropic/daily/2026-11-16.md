## Engineering problem and invariants

Agent platforms need tool interfaces that remain effective as models improve, and engineering automation that optimizes *user-observable outcomes* without gaming cheap proxy metrics. These concerns meet at the harness boundary: capability changes can invalidate once-useful scaffolding, while automated optimization can produce locally measurable but globally harmful changes.

1. **Capability alignment:** a tool's affordances must be discoverable and composable; a model must be able to invoke it correctly under the target model/harness revision.
2. **Revision and evidence binding:** benchmark, tool schema, model revision, deployment and observed result must be recorded together.
3. **Correctness over proxy:** performance ratchets must correlate with field latency and must not weaken security, functional behavior or accessibility.
4. **Bounded change:** parallel agent work, review, CI, rollout and rollback retain ownership and resource limits.
5. **Context economy:** infrequent specialist knowledge should be retrievable without occupying the main context or multiplying tool choices.

## 1. Tool affordances should evolve with model capabilities

- **Original:** [Seeing like an agent: how we design tools in Claude Code](https://claude.dev/blog/seeing-like-an-agent/)
- **Published:** 2026-04-10; **observed:** 2026-11-16
- **Classification:** First-party harness engineering case study; qualitative product observations, not a controlled benchmark.
- **Domains:** [Context and retrieval](../../../domains/context-and-retrieval.md), [Orchestration](../../../domains/orchestration.md), [Durable execution](../../../domains/durable-execution.md), [Evaluation](../../../domains/evaluation.md), [Security](../../../domains/security.md)

**Engineering question:** When does adding a specialized tool improve agent correctness, and when does it constrain an increasingly capable model or consume scarce context and action-selection bandwidth?

**Verified (publisher-reported):**

- The Claude Code team first attempted to attach user clarification questions to `ExitPlanTool`, but the combined plan/question contract confused the model; a loosely structured Markdown output was not reliably parseable. They instead introduced an `AskUserQuestion` tool that can be called at any point, presents structured options, and suspends the agent loop until the user responds.
- Early `TodoWrite` and five-turn reminders helped models stay on task, but later models were constrained by rigid to-do behavior. The team replaced this with a `Task` tool supporting cross-subagent coordination, dependencies and mutable task state.
- The initial repository-context strategy used pre-indexed RAG; the team later favored model-directed Grep/search and recursive progressive disclosure through skill files. This is a reported design evolution, not proof that retrieval indexes are generally inferior.
- The team says Claude Code had approximately **20 tools** at the time of publication and resisted adding new tools merely to expose more knowledge. For Claude Code usage questions, a dedicated guide subagent searched documentation and returned a concise answer without bloating the main agent context.

**Inferred:** Tool registries should distinguish *capabilities* from the model-visible actions exposing them. Expose small stable tool schemas for frequent actions; reveal rare knowledge via skills or specialist agents. Version and evaluate the model/tool/harness tuple, because a prompt or affordance that benefits one model can be harmful to another. A user-clarification tool is a suspended interaction with a durable pending request, not a plain text exchange.

**Alternatives:** One general-purpose shell (flexible, broad permissions and weak typed safety); many narrow tools (stronger contracts, selection burden); schema-constrained generic tools plus progressive skill discovery (lower initial context, discovery failure risk); retrieval-first context injection (lower interaction cost, freshness and relevance risk); specialist subagents (context isolation, additional tokens and coordination).

**Failure modes and unknowns:** A suspended clarification can outlive the owning session, be answered twice, or be invalidated by concurrent task edits. A skill can be stale or adversarial; a search result can refer to a different code revision. The article does not specify internal invocation success rates, tool-call confusion rates, version migration policy, or session resume semantics.

**Hypothesis / reproducible experiment:** Pin two model versions, harness SHA, tool schema set, skills revision and repository revision. Run the same 200-task corpus under (A) general shell, (B) 40 specialized tools, (C) compact tools plus skills, and (D) compact tools plus a guide subagent. Include clarification, multi-agent task dependencies, stale skill docs and ambiguous repo symbols. Record task correctness, tool selection errors, schema validation failures, p50/p95 latency, tokens, tool calls, human clarification time, and source-revision mismatches. Randomize task order and measure the interaction between model version and tool topology. Test duplicate answers and agent restarts while `AskUserQuestion` is pending.

## 2. AI-driven performance work requires calibrated proxy benchmarks and rollout evidence

- **Original:** [How we made claude.ai 3x faster in two weeks](https://claude.dev/blog/how-we-made-claude-ai-faster/)
- **Published:** 2026-09-23; **observed:** 2026-11-16
- **Classification:** First-party production engineering retrospective with vendor-reported measurements; not an independent causal experiment.
- **Domains:** [Evaluation](../../../domains/evaluation.md), [Verification](../../../domains/verification.md), [Delivery](../../../domains/delivery.md), [Orchestration](../../../domains/orchestration.md), [Context and retrieval](../../../domains/context-and-retrieval.md)

**Engineering question:** How can many coding agents optimize a large application's performance without mistaking benchmark improvement for user benefit or allowing concurrent hot-path changes to overwhelm review and release safety?

**Verified (publisher-reported):**

- Anthropic reports a two-week August sprint using Claude in Slack threads and Datadog MCP telemetry. The team identified four high-impact journeys representing approximately **95%** of user activity and defined **13** measurements with consistent start/end boundaries. It reports p75 fresh-page typeability improving from **3.1s to 0.55s**, new Claude Code session launch from **0.8s to 0.3s**, and Cowork cloud-session load from **2.6s to 0.73s**.
- For noisy latency hot paths, the team tried deterministic proxies such as Valgrind instruction counts, React commits, DOM mutations, V8 call counts and layout recalculations. They rejected proxies that failed to correlate with user-perceived wall-clock latency. Two optimized paths reduced instruction counts by **48%** and **31%**, and measured wall-clock time by **78%** and **44%**, respectively, under their reported setup. Successful metrics became CI ratchets.
- In one UI regression, an integration test delayed sidebar data until after first paint and failed on layout shifts in named regions. The author reports it failed **20/20** times on main and passed **20/20** on the fix; field telemetry subsequently indicated **31%** of web loads had some post-usable layout movement without user action.
- Work expanded to over **150 concurrent Slack threads**. The team reports over **3,000 changes** with no customer-facing incident or rollback during the sprint, but also describes human approval for every PR, unit tests, risk-scoped feature flags, staged rollout and human steering. This is not evidence that unsupervised agent merges are safe.
- A 120Hz deterministic Chromium frame-stepping harness measured streaming render behavior against an **8.33ms/frame** budget. Reported main-thread blocking on long answers fell from roughly **750ms to 200ms** in one optimization effort, with nightly regression checks.

**Inferred:** A productive optimization platform needs a metric ladder: real-user field outcome -> reproducible lab proxy -> version-bound CI ratchet. Every candidate proxy must demonstrate correlation with field outcomes and must be retired if misleading. Parallel agents can search the optimization space, but humans should own user-impact trade-offs and release risk. Performance improvements must remain constrained by functional tests, safety, accessibility and rollbacks.

**Alternatives:** Manual profiling and periodic performance sprints (slow feedback, lower coordination); deterministic microbenchmark-only gates (fast, Goodhart risk); RUM-only optimization (authentic but noisy and slow); mixed RUM/lab/CI ratchet with feature flags (stronger attribution, higher instrumentation and operational cost).

**Failure modes and unknowns:** Proxy benchmarks can reward deleting useful behavior; warmed caches can conceal cold-load regressions; a lab browser can omit real browser chrome and device behavior. More agents can increase merge conflicts, CI load and human attention. The article does not disclose exact PR denominator by risk tier, confidence intervals, total compute cost, experiment control group, or whether all reported improvements persisted across subsequent months.

**Hypothesis / reproducible experiment:** Pin a web-app source SHA, browser/runtime versions, device classes, cache state, synthetic journey traces and a field RUM schema. For four high-volume journeys compare (A) manual profiling, (B) agent-only microbenchmark ratchets, and (C) agent optimization with lab-to-field calibration, review and feature flags. Run at 1/10/100 concurrent agents with CI and merge contention injected. Require benchmark-to-RUM correlation with confidence intervals and test cold/warm, 60/120Hz, low-memory and slow-network cases. Measure p50/p75/p95 interaction latency, frame drops, correctness/accessibility regressions, reverted changes, incident rate, CI compute minutes, agent token cost and human review minutes. Intentionally insert a benchmark-gaming change to verify gate rejection.

## Synthesis and next validation

**Verified (source-supported):** These two publications disclose an adaptive tool-design process and a human-supervised, highly instrumented performance engineering workflow. Reported numbers describe Anthropic's specific products, time windows and measurement setup.

**Inferred:** The reusable pattern is **versioned capability discovery + task-relevant context + calibrated evaluation + guarded release**. More tools and more agent threads are not automatically better; both expand the coordination and verification surface.

**Hypothesis:** Maintaining a small model-visible tool surface and a metric ladder that links lab proxies to user outcomes can improve correct changes per unit of agent, CI and human cost.

**Unknown:** The optimum tool count, capability discovery strategy, number of concurrent agents and benchmark proxy mix are workload-, model- and environment-dependent. Neither article independently proves a universal setting.

**Next actions:** Reproduce tool-topology A/B tests against pinned models and task sets; prototype a performance ratchet with false-positive/false-negative validation; bind each automated optimization PR to benchmark revision, source SHA, field evidence and rollback owner.

No source-code audit, live system experiment or independent reproduction was conducted for this intake.
