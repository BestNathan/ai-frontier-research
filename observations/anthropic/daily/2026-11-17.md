## Engineering problem: independent evidence at agent throughput

When autonomous coding agents write, test, review and merge changes, they may also author the tests and evaluation criteria that declare their own work correct. A passing test can be stale, flaky, self-serving, or associated with a different source revision. The problem is not simply producing more tests; it is maintaining **independent, attributable and reproducible verification evidence** as the number of concurrent authors grows.

### System boundary and invariants

1. **Evidence identity:** Every gate decision must bind source commit SHA, base revision, check definition/policy revision, test input or workload, environment fingerprint, execution time and result. A new commit invalidates any evidence whose dependency set changed.
2. **Independent authority:** The untrusted change cannot rewrite the rule that decides its acceptance. The rule must be read from a protected base or policy revision; modifications to check definitions are independently reviewed.
3. **End-to-end semantics:** Tests must validate user-observable behavior, not merely agent-generated local assertions. Test oracles must be derived from externally owned requirements where possible.
4. **Deterministic invariants:** Property-based tests should expose edge cases, round-trip failures, idempotency violations and equivalence regressions; differential tests need a pinned reference implementation and a documented list of expected differences.
5. **Bounded escalation:** Automated repair/review must terminate after a finite budget and produce actionable human escalation. A retry of a flaky test is not equivalent to a verified fix.
6. **Safe promotion:** Review outcomes are evidence, not authority to bypass release/security policy; critical paths and irreversible side effects retain independent gates.

### Verified — first-party author reports, not independently reproduced

- The author reports that approximately **90%** of the Claude Code team's code is written and reviewed by Claude. This is an internal share estimate, not a measured industry baseline.
- The article recommends three complementary verifier classes: **end-to-end tests** that execute user flows with screenshots/traces; **property-based tests** (for example fast-check, Hypothesis or proptest) that generate invariant-breaking inputs; and **differential tests** that compare a new implementation against a reference under identical inputs, with explicitly approved deviations.
- The team reportedly packages application-specific smoke testing in a repository-local `.claude/skills/verify` skill. The agent starts and drives the real app/service before committing. The source does not publish a universal `verify` schema or guarantee that all product paths have this integration.
- Automated repair is reportedly capped: after **three** unsuccessful rounds, a person is involved. Code owners define and tune their own checks so the alert includes why it fired.
- The author describes a **39-item** reliability checklist with diff-based triggers. Typically **3–10** checks apply to a given diff. One example is backwards compatibility of `--resume` when transcript/session message structures change. These counts describe this team's current practice, not a normative checklist size.
- The source says `REVIEW.md` for review policy is read from the **base/default branch**, not the PR branch. Reviews apply to **specific commits**, and the team runs cheaper checks before consuming shared review/CI resources.
- Commit verification stamps can record the absence of verification as `none`. A gate supports **off**, **observe**, and **enforce** modes; in the reported implementation, after two blocked commits in a session the next attempt is allowed through to prevent an agent deadlock. This escape hatch is a policy trade-off, **not** proof of safe verification.
- Review quality is measured using historical incident/revert changes and stable control changes, with separate recall measurements for **raw findings**, **post-verification findings**, and **final review output**. The author describes converting recurrent human-review/revert patterns into rules, using three agents to try to falsify candidates before human approval.
- The article refers to an internal structured-file-generation evaluation in which a separate rubric-based grader improved task success **by up to 10 percentage points**. The effect is vendor-reported, bounded to that evaluation, and not evidence of a universal improvement.

### Inferred — engineering interpretation

A verification platform should be a **separate evidence and policy control plane**. The agent may generate candidate tests and run tools, but cannot unilaterally change the acceptance policy that judges the candidate. A minimal evidence tuple is `{head_sha, base_sha, policy_sha, test_definition_sha, environment_digest, workload_id, run_id, result, timestamp}`, with immutable log storage and explicit invalidation rules.

Diff-triggered reliability checks can reduce CI and review costs, but they are a *selector*, not a complete safety argument. Any missing dependency graph, renamed path, generated artifact or cross-module behavior may make a relevant check invisible. For critical invariants, retain a mandatory test floor or conservative fallback. The base-branch policy rule addresses self-editing within a PR, but policy repository ownership, review permissions, external scripts, CI runner integrity and protected-branch changes remain separate attack surfaces.

The three-strike human escalation and two-block escape hatch are different mechanisms. The first bounds unproductive autonomous repair; the second deliberately weakens a commit gate to preserve liveness. A platform must distinguish **allowing a local commit** from **approving a protected merge or production release**. The latter should never be bypassed by an agent retry counter.

### Alternatives and trade-offs

| Approach | Benefit | Failure / cost |
| --- | --- | --- |
| Human-only review plus unit tests | Simple accountability | Attention bottleneck, weak end-to-end coverage |
| Agent-authored tests with no independent policy | Fast iteration | Self-confirming oracle, mutable gate, benchmark gaming |
| Independent static/policy gates and full E2E on every commit | Stronger isolation | Slow, flaky, expensive at scale |
| Risk-weighted property/differential/E2E tests plus protected policy and evidence store | Coverage matched to change risk | Selector false negatives, infrastructure complexity, evidence retention |
| Historical incident replay for reviewer tuning | Concrete defect recall and controls | Distribution shift, incident selection bias, overfitting to known regressions |

### Failure modes, limitations and Unknown

- **Stale SHA:** PR changes after successful review; evidence must be invalidated or recomputed.
- **Self-editing policy:** PR modifies `REVIEW.md`, CI workflow, test harness or dependency; protect policy revisions and ownership separately.
- **Correlated author/checker bias:** The same agent invents both a change and the assertion that validates it. Independent reference oracles and incident replays mitigate but do not eliminate this.
- **Flaky feedback:** Agent learns to retry, sleep or delete checks rather than fix the underlying race. Test ownership and reproducible failure capture are required.
- **Differential false positives:** Normalization can hide meaningful output differences; the reference can itself contain bugs.
- **Escalation bypass:** Local liveness exceptions must not become merge authorization.
- **Unknown:** Internal check selection implementation, source revisions, deployment scope, denominators for ~90% code share, cost per verified change, CI false-negative rates, exact review policy permissions and whether reported gains persist across model changes. No source-code audit or independent execution was performed.

### Hypothesis and falsifiable experiment

**Hypothesis:** Protected, revision-bound verifier policies with risk-weighted E2E/property/differential checks reduce escaped defects per verified merge and human review minutes compared with agent-authored tests and unprotected review rules, even when agent throughput increases.

**Setup:** Pin application repository SHA, agent model and harness version, runner image digest, policy SHA and test suite revisions. Prepare a stratified corpus of 150 historical PRs (50 known incident/revert defects, 50 clean controls, 50 ordinary feature changes), plus injected regression cases: stale transcript resume, concurrent tool retry duplication, JSON round-trip, broken permission boundary and a PR that edits its own review policy. Do not leak incident labels to the review agents. Randomize order; repeat each condition at least three times.

**Arms:** (A) unit tests and human review; (B) agent-authored tests plus a mutable PR-local reviewer policy; (C) protected base-branch policy with full E2E/property/differential verification; (D) protected policy with diff-triggered checks and mandatory critical-risk floors. Test 1/10/50 concurrent agents under controlled CI resource budgets.

**Measures:** escaped defects per 100 accepted changes; precision and recall separately at raw, verified and final finding stages; false-negative selector rate; stale-result acceptance; p50/p95 verification latency; flaky retry counts; CI CPU-minutes; model tokens; human minutes; rollback rate. Verify that a post-review commit invalidates the old evidence, a PR policy edit cannot relax the gate, and a two-block local bypass cannot authorize a protected merge.

**Falsification:** Reject the hypothesis if the protected-policy arms fail to reduce escaped defects or total review cost within confidence intervals, or if diff-triggered selection misses critical regressions relative to full verification.

## Synthesis and follow-up

**Verified (source-supported):** Anthropic publicly describes a practical combination of E2E, property and differential tests; code-owner checks; a diff-triggered reliability checklist; commit-specific reviews; base-branch reviewer policy; finite agent repair loops; and historical-incident-based reviewer evaluation.

**Inferred:** The transferable infrastructure pattern is **policy isolation + revision-bound evidence + selective verification + human escalation**, not a specific checklist size or model-specific skill file.

**Hypothesis:** Evidence identity and protected policy can improve verified delivery per unit CI and human cost as agent concurrency rises.

**Unknown:** The private implementation's completeness and causal impact; all reported measurements remain author claims until reproduced.
