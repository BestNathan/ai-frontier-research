# Environment Enforcement and Capability Containment as Agent Infrastructure Invariants

**Observed:** 2026-11-18

## Research question and system boundaries

**Problem:** When a model uses a real execution environment, both the *measured capability* and the *reachable damage* depend on external infrastructure. A model-centric metric or approval policy is insufficient to describe the actual system.

Two invariants:

1. **Evaluation comparability:** A reported score must be bound to the model, harness, workload, resource reservation and hard limit, runtime enforcement, timing, failure taxonomy, environment and repetitions. Avoid conflating model failure with infrastructure failure.
2. **Capability containment:** An agent may only perform authorized effects, even if it follows an adversarial instruction, receives malicious tool output or obtains elevated rights within a guest. Trust should attach to identity, operation, data provenance and destination, not merely to a URL or an "approved" tool name.

These are related but different control planes: resource enforcement determines which strategies are *possible*, while security enforcement determines which effects are *permitted*.

## 1. Resource enforcement is a first-class evaluation variable

- **Original:** [Quantifying infrastructure noise in agentic coding evals](https://www.anthropic.com/research/infrastructure-noise)
- **Published:** 2026-02-05; **observed:** 2026-11-18
- **Authors:** Gian Segato and collaborators; first-party Engineering research
- **Infrastructure domains:** [Evaluation](../../../domains/evaluation.md), [Verification](../../../domains/verification.md), [Orchestration](../../../domains/orchestration.md), [Durable execution](../../../domains/durable-execution.md)

### Problem and mechanism

Agentic coding benchmarks run a model *and* its tools in a resource-limited environment. Kubernetes-style reserved resources (guaranteed allocation) and hard cgroup/container limits are distinct; setting both to a nominal per-task spec can cause transient OOM termination. Adding headroom initially improves infrastructure reliability, but eventually permits memory-heavy solving strategies that change what the benchmark measures.

### Verified — source-supported, vendor-reported

- Anthropic reports Terminal-Bench 2.0 experiments on Google Kubernetes Engine using six resource configurations with the same Claude model, harness and tasks. Infrastructure failure decreased from **5.8%** at strict 1x enforcement to **0.5%** when uncapped. Strict to 3x headroom reduced failures to **2.1%** (reported p < 0.001).
- Between 1x and 3x, benchmark success differences were within experimental noise (reported p = 0.40). From 3x to uncapped, infrastructure errors fell another **1.6 percentage points** while success rose almost **4 points**. Overall 1x-to-uncapped success improvement was **6 percentage points** (reported p < 0.01).
- A SWE-bench crossover experiment on **227 tasks with 10 samples each** increased RAM up to 5x; success increased **1.54 percentage points** at 5x versus 1x, according to the article.
- The author explicitly distinguishes benchmark score changes due to eliminated infrastructure errors from changes in the set of strategies an agent can execute. Time limits, concurrency, network bandwidth, hardware and API latency may also confound measurements; time-of-day effects were described as anecdotal, not quantified.

### Inferred — architecture implications

A benchmark manifest should include `{model_version, harness_version, dataset_sha, image_digest, task_id, cpu_request, cpu_limit, memory_request, memory_limit, timeout, concurrency, egress_policy, node_class, run_id, timestamp, result, failure_category}`. For Linux cgroup v2, capture `memory.max`, `memory.high` (if used), `memory.events`, CPU throttling and OOM events. Distinguish platform crash, workload timeout, agent failure and verifier failure in a stable taxonomy.

Do **not** generalize "3x" as a universal recommended multiplier: it was a calibration outcome for a particular benchmark and configuration. The actual target is an empirically identified headroom band where infrastructure error rates decrease without statistically meaningful task-success inflation.

### Alternatives and costs

| Enforcement strategy | Benefit | Risk / cost |
| --- | --- | --- |
| Request equals hard limit | Repeatable nominal resource budget | OOM spikes and false benchmark failures |
| Separate request and calibrated ceiling | Reduces infrastructure failures with a bounded resource envelope | Needs per-workload calibration and extra capacity |
| Uncapped execution | Few resource kills | Changes solution strategy, costs and score comparability |
| Multiple published resource tiers | Exposes capability-resource Pareto frontier | More runs, analysis and operational cost |
| Fixed dedicated machines | Reduces shared-cluster variability | Expensive, still needs explicit limits and versioning |

### Unknown and validity limits

The article does not publish every task-level raw result, exact node-level contention, complete model-by-model confidence intervals or a cross-vendor causal study. GKE enforcement behavior does not by itself establish all providers' sandbox implementations. A p-value is not proof of transportability across workloads. The reported differences are not independently reproduced here.

### Falsifiable experiment

Run Terminal-Bench 2.0 and a version-pinned coding workload on a fixed model, prompt, harness and dataset SHA with `1x/1.5x/2x/3x/5x` resource ceilings and constant requests; separately vary CPU and RAM. Use at least 10 repeated seeds/task where feasible and paired task comparisons. Measure verified solve rate with confidence intervals, infra-failure rate, OOM and CPU-throttle events, p50/p95 duration, GPU/model tokens, sandbox CPU/RAM-hours, dollars per verified solve and operator intervention. Add injected memory spikes and node contention; report whether ranking reverses and at what ceiling. The hypothesis is falsified if calibrated headroom fails to lower infrastructure errors without increasing solve rate for a matched baseline.

## 2. Agent security is an end-to-end capability graph, not a sandbox toggle

- **Original:** [How we contain Claude across products](https://www.anthropic.com/research/how-we-contain-claude)
- **Published:** 2026-05-25; **observed:** 2026-11-18
- **Authors:** Max McGuinness, Mikaela Grace, Jiri De Jonghe, Jake Eaton, Abel Ribbink; first-party Engineering disclosure
- **Infrastructure domains:** [Security](../../../domains/security.md), [Durable execution](../../../domains/durable-execution.md), [Orchestration](../../../domains/orchestration.md), [Evaluation](../../../domains/evaluation.md)

### Problem and mechanism

The probability of an unsafe action and the blast radius of a permitted action are separate dimensions. Human approvals and model classifiers are probabilistic; isolation, mounts, credential custody, egress restrictions and operation-level policy can deterministically limit *reachable* effects if the implementation and its trusted computing base hold.

The article distinguishes three sources of risk (user misuse, model misbehavior, external attacker) and three defense surfaces (environment, model, external/tool content). It compares server-side ephemeral gVisor containers, local OS-level sandboxes (macOS Seatbelt and Linux bubblewrap) and local VMs. These are product-specific patterns, not evidence of one universal architecture.

### Verified — source-supported, vendor-reported

- Anthropic reports users approved about **93%** of Claude Code permission prompts, motivating fewer repetitive approvals and more enforceable boundaries. The OS sandbox reportedly reduced prompts **84%**. These are internal telemetry figures without independent audit.
- In Claude Code, project-local configuration could be parsed and a malicious hook run **before** the workspace trust prompt. The reported fix was to defer parsing and execution until the trust boundary had been established. "Local" input is not necessarily trusted.
- In an internal red-team phishing exercise, a malicious prompt presented as user instructions reportedly succeeded at credential exfiltration in **24 of 25** retries. Model-layer user-intent checks did not reliably identify the attack. This is a bounded adversarial scenario, not an estimated population-wide rate.
- Cowork originally ran its entire agent loop inside a local VM; moving the loop to the host while retaining VM-contained tool execution improved recoverability when VM startup failed. Local MCP servers were also moved outside the VM for auditability, dependency management and host integrations; this explicitly expands the host-side trust boundary.
- A reported third-party vulnerability used an **allowed** Anthropic API domain with an attacker-controlled API key to upload workspace data. Domain allowlisting passed the request. Anthropic describes an intercepting proxy requiring the VM's own provisioned session token and blocking headers that enable server-side fetch. An allowed hostname is therefore not a sufficient capability boundary.
- The article distinguishes read-only, read-write and read-write-no-delete mount modes, notes that symlinks must be resolved before path validation, and describes credentials remaining in host custody with per-session scoped tokens for the VM.
- VM isolation also obstructed host EDR visibility. The article describes pull-based OTLP exports for after-the-fact event inspection, explicitly **not** equivalent to live guest monitoring.
- For remote MCP, connector code approval does not imply approval of subsequent remote behavior or data. Tool responses, persistent memory and subagent summaries can carry prompt injection and trust escalation across sessions.

### Inferred — security design implications

Represent each agent capability as a grant over `{principal, session, tool, operation, resource, destination, credential_scope, data_class, expiry, audit_id}`; verify at a trusted boundary **outside** the model and, where practical, outside the tool-execution sandbox. Network egress should be evaluated as a *function-level* capability: method, endpoint, account/tenant identity, token provenance and allowed data classes, not merely hostname.

The model/harness can run outside a failed sandbox to preserve observability and recovery, but it must not silently inherit unrestricted host execution. Local MCP servers must be treated as host-level software with separately reviewed permissions. Persistent memory and session history require source provenance and scanning on rehydration, not just on initial retrieval.

A minimal trust graph contains: user identity, agent/session principal, policy authority, model/harness, sandbox worker, filesystem mounts, MCP/other tools, network proxy, secret broker, audit/event sink and external account/tenant. Every boundary crossing should have explicit denial and revocation semantics.

### Alternatives and costs

| Architecture | Advantage | Threat / operational cost |
| --- | --- | --- |
| Prompt approvals + unrestricted host tools | Low runtime overhead, familiar developer workflow | Approval fatigue, catastrophic blast radius |
| OS sandbox + scoped workspace and egress | Fast startup, native tool compatibility | Kernel/namespace/policy implementation and local-host tool exceptions |
| Full VM including agent loop | Strong guest boundary, clear host/guest split | Boot failures can prevent recovery and diagnosis |
| Host harness + isolated VM/tool worker | Better control-plane availability during worker failure | Requires strict tool mediation and host MCP trust handling |
| Domain-only proxy | Easy policy expression | Authorized-domain exfiltration and tenant confusion |
| Identity/operation-aware proxy + secret broker | More precise effect constraints | Proxy becomes high-value trusted code and audit surface |

### Failure modes and Unknown

- **Pre-trust config execution:** A project file triggers a hook before the user accepts trust.
- **Symlink escape:** A mounted path is validated before canonical resolution.
- **Allowed-domain exfiltration:** A different account/API key uses a legitimate endpoint.
- **Agent identity confusion:** A child agent or local MCP inherits broader host authority.
- **Persistent injection:** A poisoned memory note survives restarts and is promoted to instruction.
- **Blind telemetry:** Host EDR cannot inspect a guest; delayed OTLP cannot stop an ongoing incident.
- **Recovery bypass:** After VM crash, a privileged host-side fallback executes a tool outside the intended boundary.

**Unknown:** Full implementation of the custom proxy, independent exploit reproduction, tenant-level authorization model, guarantees of read-write-no-delete under all filesystem operations, exact latency/cost of monitoring, and failure semantics when secret broker or policy authority is unreachable. The source does not establish that all versions of every product implement every mitigation.

### Falsifiable experiment

Create a *non-production* sandbox testbed with dummy credentials and synthetic sensitive files, and evaluate four policy modes: approvals only, OS sandbox, VM isolation, and VM/OS sandbox with identity-aware proxy and scoped secret broker. Run benign coding workflows plus adversarial fixtures: pre-trust project hooks, symlink traversal, poisoned MCP tool output, a session-memory injection, an approved-domain cross-account upload attempt, worker restart and network partition. Never use real secrets or public exfiltration endpoints.

Measure unauthorized read/write/network effects, false denials, per-session capability revocation latency, p95 tool latency, cold-start/recovery time, audit completeness, EDR/OTLP detection lag, CPU/RAM overhead and operator review burden. The hypothesis is falsified if the stricter capability graph does not reduce unauthorized effects compared with hostname-only and approval-only policies at a bounded performance cost.

## Cross-study synthesis and decisions

**Verified (publisher reports):** Evaluation resource limits materially change observed coding success and infrastructure errors; agent permissions and proxies materially change reachable external effects. Both are properties of the *whole execution system*, not model weights.

**Inferred:** The sandbox manifest should be versioned and auditable as part of both evaluation provenance and capability authorization. Keep resource allocation policy distinct from security capability policy; a generous memory ceiling should not grant broader file/network permissions.

**Hypothesis:** Binding execution evidence to resource enforcement plus operation-scoped capabilities reduces misleading benchmark comparisons and unauthorized tool effects while retaining recoverability.

**Unknown:** Cross-vendor generalization, production cost of per-operation authorization, and whether a unified manifest makes the trusted control plane too complex to audit.

**Follow-up:** Build a reproducible `execution_envelope` manifest and compare it against a bare container spec in both benchmarking and adversarial tool workloads. Evaluate policy provenance, enforcement, failure classification and evidence retention. No live system or independent source-code audit was performed in this intake.
