**Observed:** 2026-11-20  
**Fresh publication window screened:** 2026-11-18–2026-11-20. No new implementation-level engineering article was confirmed in the current first-party listings.

**Evidence type:** First-party engineering playbooks with illustrative/internal measurements. No independent benchmark reproduction or code audit was performed.

## Engineering problem: how can an agent change its own optimization surface without invalidating the evidence, while executing in a disposable remote environment?

The two concerns have a shared invariant: **the candidate change, evaluation oracle, execution identity, resource envelope, and persistent state must remain independently attributable**. An agent may iterate on prompts, skills, harnesses and code, but should not be able to manufacture the benchmark answer or lose uncommitted work when a remote execution environment expires.

A successful experiment must identify `{task_corpus_sha, train_split_sha, holdout_split_sha, grader_sha, agent_config_sha, source_sha, environment_digest, resource_limits, run_id, result, token_cost, human_review_minutes}`. The exact record is a proposed abstraction, **not** a disclosed Anthropic schema.

## 1. Guarding the evaluation oracle during automated hillclimbing

- **Primary original:** [Automating eval design and hillclimbing with Claude](https://claude.dev/blog/automating-eval-design-and-hillclimbing/)
- **Published:** 2026-09-28; **observed:** 2026-11-20
- **Author:** Lance Martin, Claude Developer Blog, Playbooks
- **Domains:** [Evaluation](../../../domains/evaluation.md), [Verification](../../../domains/verification.md), [Context and retrieval](../../../domains/context-and-retrieval.md), [Delivery](../../../domains/delivery.md), [Security](../../../domains/security.md)

### Verified — source-supported first-party disclosure, not independent validation

- The Claude Code `claude-api` skill offers `/claude-api build-eval` and `/claude-api hillclimb`. The article describes an approval-driven eval builder and a change-one-thing-at-a-time optimizer. This is a published playbook, not an audited implementation contract.
- Eval construction favors production traces (subject to retention/privacy review), support tickets, human-written examples and then code-grounded synthetic examples. A person approves candidate examples and grader behavior; case-level transcripts and repeated runs are retained.
- The author proposes four quality criteria: realistic task distribution, sensible capability/effort ordering, non-saturated passable headroom and low variance. The builder reportedly checks grader repeatability, timeout/API/cutoff contamination and whether baseline accuracy is already around 95%.
- Hillclimbing separates visible training failures from a held-out test split. Candidate modifications can affect prompt, skills, tool descriptions, model/effort or harness code. Each round proposes one patch; train-only improvement is treated as overfitting and reverted, while regression is reverted. The article warns about reference-answer leakage and agents adding benchmark-specific capabilities.
- The article reports a **44-ticket** internal support example, split **30 search / 14 held out**. A sequence of prompt/model changes reduced reported per-ticket token cost from **4.6 cents to roughly 1 cent** at an intermediate point, with later prompt tuning. On the 14 held-out tickets, the author reports **90.5%** for the final setup versus **78.6%** for the baseline, at roughly one-fifth the cost. With such a small holdout, this is illustrative and not a statistically robust general benchmark.
- In a separate `claude-api` skill eval, reported score improved from approximately **66% to 88%** through missing feature coverage, correcting language/API tables, countering stale model priors and fixing contradictory tasks/graders. Some apparent failures were evaluator defects rather than model defects.
- The author recommends confidence intervals, checking the evaluation's noise floor before iterating, root-cause grouping after two or three stalled rounds, and declining to merge when observed improvement is within noise.

### Inferred — protected optimization and evidence plane

A reliable optimizer needs three independently controlled surfaces: (1) **candidate configuration** that the agent may edit; (2) **protected task set, split assignments and grader** that it cannot change unilaterally; and (3) **immutable run evidence** that binds candidate, oracle, environment and outcomes. The held-out split should be inaccessible to the patch-generating agent, including through tool outputs, filesystem paths, repository history, logs and error messages.

There is an important distinction between *using* a holdout score to select among many iterations and preserving a truly untouched final test set. Repeatedly checking a fixed holdout to choose patches can itself overfit that holdout. Use a training set for patch design, a validation set for early stopping and a separate locked final test set for unbiased acceptance; rotate or replenish after repeated campaigns. The article's described train/test workflow is not evidence that this stronger separation is already implemented.

**Threat model:** A malicious or merely reward-seeking agent can read hidden answers, change grading logic, inject examples, optimize a misleading metric, or exploit environment leakage. Even without intent, a grader can misclassify legitimate solutions and resource limits can change model strategy.

### Alternatives and costs

| Strategy | Benefit | Failure or cost |
| --- | --- | --- |
| Manual eval and prompt review | Simple control and accountability | Slow, small coverage and subjective judgments |
| Fully autonomous optimization on one public benchmark | Fast and inexpensive iteration | Data leakage, benchmark memorization, self-modifying oracle |
| Train/validation split with locked grader | Detects some regressions and overfitting | Repeated validation peeking and grader drift |
| Protected three-way split, versioned grader, immutable evidence | Better independent final acceptance | Additional cases, access controls, repeated inference and human review |
| Online A/B evaluation with controlled rollout | Production representativeness | Safety, exposure, interference and rollback complexity |

### Unknown and limitations

The source does not disclose a complete implementation of split isolation, code execution sandbox, CI policy, permissions, evaluator versioning, exact random seeds or raw per-case data. The published examples do not establish that hillclimbing improves every agent system or that held-out scores remain unbiased after many candidate trials. No source-code revision was inspected.

### Falsifiable experiment

**Hypothesis:** An optimizer with a protected final test set, versioned oracle and isolated candidate patching improves *out-of-sample verified correctness per dollar* more reliably than unrestricted benchmark hillclimbing.

Pin an application source SHA, 300+ stratified cases from production-like tasks, an independently reviewed grader, fixed model/effort, sandbox image, network/secret policy, CPU/RAM ceiling and repetition seeds. Randomize multiple campaigns across (A) human prompt tuning, (B) one-split autonomous optimization, (C) train/validation hillclimbing, and (D) protected train/validation/final-test plus independent acceptance. Include ambiguous cases, prompt-injection artifacts, a deliberately misleading grader, duplicated examples and canary answers inaccessible to the agent.

Measure final untouched-test success with confidence intervals, grader disagreement, leakage attempts, train-to-test gap, p50/p95 latency, token and sandbox cost, rollback frequency, reviewer time, and rate of accepted changes later rejected by an independent oracle. The hypothesis fails if D does not improve final-test correctness/cost or materially raises the false-acceptance rate. Register the selection rule before observing final results.

## 2. Cloud sessions require independent identity, secret custody and durable source state

- **Primary original:** [Claude Code in the cloud: a field guide to cloud sessions](https://claude.dev/blog/claude-code-in-the-cloud/)
- **Published:** 2026-10-06; **observed:** 2026-11-20
- **Author:** Addy Osmani, Claude Developer Blog, Playbooks
- **Domains:** [Durable execution](../../../domains/durable-execution.md), [Source control](../../../domains/source-control.md), [Security](../../../domains/security.md), [Orchestration](../../../domains/orchestration.md), [Verification](../../../domains/verification.md), [Evaluation](../../../domains/evaluation.md)

### Verified — source-supported first-party disclosure, not an implementation audit

- The author describes one fresh VM and Git branch per cloud task, avoiding shared working trees and port collisions. Sessions may be initiated or followed from browser, mobile, desktop, CLI or Slack.
- A GitHub proxy reportedly keeps the user's long-lived GitHub token **outside the VM**. The session receives a short-lived, branch-scoped credential; other network traffic passes through an egress proxy with configurable restrictions. This is a vendor description, not an independently verified proof of complete confinement.
- Repository-local `CLAUDE.md`, skills, agents and settings travel with the repository, while personal `~/.claude` configuration does not. An idle VM can be reclaimed and later replaced with a fresh VM while restoring the conversation. The author warns that **uncommitted filesystem changes may not survive** and recommends committing progress.
- The article distinguishes environment setup scripts, cached tool files and per-session processes. Setup scripts run as root, the cache can be rebuilt on configuration changes and roughly weekly, and running services do not survive the cache. Repository `SessionStart` hooks can restore project dependencies/services.
- The article notes that even a strict egress mode may still allow Anthropic model API traffic and branch pushes; a network allowlist is not a complete data-exfiltration or capability boundary.
- In a small illustrative repository, the author started three independent cloud tasks within **16 seconds**; their reported durations were approximately **62, 65 and 87 seconds**, with task-specific verification. This is a field-guide example, not a representative concurrency benchmark.
- The guide describes remote session teleportation and routine triggers (schedule, HTTP and GitHub events), with unattended runs using automatic permission modes. It also warns that parallel sessions consume model plan quotas concurrently.
- The source reports self-hosted environments as a beta option for organizations, but does not publish a full state migration, failover, token-issuance or network proxy protocol.

### Inferred — separate persistent control plane from disposable execution

A robust cloud-agent platform should model **task identity**, **execution lease**, **conversation/event log**, **source revision and branch**, **sandbox instance**, **credential capability**, and **approval policy** separately. A VM is a replaceable execution lease, not the durable session identity. Persist progress in a revisioned source-control branch plus a control-plane event log, and reconcile actual branch/deployment state after restarts rather than blindly replaying prior tool calls.

A short-lived GitHub credential is a capability token with explicit `{subject, repository, branch, operations, expiry, audit_id}`; these are proposed attributes, not an Anthropic token schema. Enforce branch restrictions at the proxy/server, not only in model instructions. Repo-local hooks and setup scripts must be treated as executable, potentially untrusted code; their root execution expands the attack surface.

**Failure model:** VM reclaimed with dirty files; branch push acknowledged but tool response lost; credential expires mid-push; setup cache contains stale dependencies; concurrent sessions edit a shared base; malicious repository hook accesses environment secrets; network proxy allows API-mediated exfiltration; reviewer teleports onto a different commit than the verified result.

### Alternatives and costs

| Model | Advantage | Failure or cost |
| --- | --- | --- |
| Local session sharing developer host | Immediate private services and low provisioning latency | Broad host credentials, dirty workspace interference, laptop availability |
| Local worktree per agent | Branch isolation without new VMs | Shared host credentials/process/network and resource contention |
| Disposable remote VM per task | Stronger workspace/process isolation, asynchronous work | Startup, image/cache management, state loss, cloud cost and policy complexity |
| Long-lived remote sandbox | Warm dependencies and continuity | Persistent compromise and state drift, idle resource cost |
| Ephemeral sandbox with durable event/source state and external credential broker | Recoverability and explicit authority boundaries | More control-plane coordination, retries and audit obligations |

### Unknown and limitations

No exact VM implementation, token issuance protocol, tenant isolation proof, consistency semantics for restored transcripts, secret proxy security review or full end-to-end cost accounting is published. The guide's example timings do not establish p95 startup or fleet economics. A branch-scoped credential alone does not protect other resources reachable through tools or model API egress.

### Falsifiable experiment

**Hypothesis:** Ephemeral per-task VMs with a durable event log, branch-scoped credentials and explicit restart reconciliation reduce cross-session interference and secret exposure without unacceptable recovery cost compared with shared-host worktrees.

Run a fixed 100-task coding corpus under (A) local shared host, (B) local isolated worktrees, (C) remote per-task VMs with transcript-only restoration, (D) remote per-task VMs with durable branch+event checkpoints. Pin model, harness, base SHA, setup script SHA, image digest, egress policy, Git credential scopes, node class and task budget. Inject VM reclamation before commit, lost push acknowledgments, token expiry, failed root setup, malicious hooks and concurrent branch conflicts. Measure verified completed tasks, recovery correctness, uncommitted-work loss, unauthorized operation attempts, secret access, p50/p95 provisioning and resume latency, model tokens, VM-hours, reviewer time and dollars per verified delivery.

The hypothesis fails if D does not improve recovery and isolation over C or if its overhead exceeds a pre-registered cost/latency budget. Do not claim a security boundary is proven solely by a successful benign test.

## Cross-source synthesis and next actions

**Verified (first-party reports):** One source describes optimization driven by task/grader evidence and train/holdout separation; the other describes task-isolated cloud execution with external credential custody and VM reclamation. These are separate product mechanisms.

**Inferred:** Their combination motivates an **evidence-bound, lease-based agent execution contract**: a candidate configuration may evolve, but the authoritative test oracle and acceptance policy stay outside the candidate's edit scope, and the disposable execution environment never owns the durable task identity or long-lived secrets.

**Hypothesis:** Versioning oracle, source, environment, permission and result together improves reproducibility and safety under parallel, self-optimizing agents.

**Unknown:** Whether Anthropic's internal eval and cloud-session platforms share infrastructure, protocols, or a common policy authority. The sources do not establish this.

**Next:** Build a small reference benchmark with three-way split protection and crash/retry injection, then compare the effect of short-lived execution leases and independent evidence gates on correctness per total cost. Treat all vendor performance numbers as first-party claims until independently reproduced.
