## Engineering problem and invariants

**Question:** When should a long-running coding platform introduce planner, evaluator, sprint, and context-reset machinery, and when should a stronger base model make those components unnecessary?

A useful harness must produce correct, complete, recoverable software **per unit of total cost**, rather than maximize the number of agents, iterations, or generated features.

Candidate invariants (our synthesis, **not** Anthropic's published internal contract):

1. Acceptance criteria are frozen **before** the corresponding implementation attempt, and evaluation evidence is bound to a code revision, verifier version and execution environment.
2. Planner-generated scope must be distinguishable from user-authorized requirements; a model may propose features without silently elevating them into mandatory acceptance.
3. Evaluators are separated from generators in execution and feedback provenance, but are not automatically independent or unbiased simply because they are separate agents.
4. Every restart, compaction or handoff retains authoritative task state and a recoverable source revision; summaries are derived context, not authoritative history.
5. The scheduler bounds wall time, tokens, API spend, evaluator rounds, concurrent workers and human review; expensive iteration requires measurable marginal quality improvement.

## Verified — source-supported author disclosures

### 1. The three-agent feedback architecture

- The author built a **planner → generator → evaluator** structure using the Claude Agent SDK. The planner expanded a short prompt into a product specification; the generator implemented features; an evaluator inspected a running application using **Playwright MCP**, including UI interactions, API behavior and database state.
- In the initial full-stack version, the generator and evaluator negotiated a **per-sprint contract** defining observable behaviors and success criteria before the generator wrote code. Their messages were exchanged through files. The evaluator applied per-criterion thresholds and returned concrete failures for revision.
- The author reports that Claude's uncalibrated self-evaluation was often overly generous; even a separate evaluator required repeated prompt calibration against human judgment and still missed some defects.
- For frontend design, the evaluator used four dimensions: **design quality, originality, craft and functionality**. Few-shot score calibration and live browser inspection supported 5–15 iteration cycles, with some runs taking up to four hours. The author notes that later iterations were not always preferable to intermediate ones.

### 2. Context reset is a model-conditional workaround

- The author's earlier harness used fresh context plus structured handoffs to address premature task termination near context limits in **Sonnet 4.5**. The article distinguishes that mechanism from in-place compaction and acknowledges reset overhead.
- With **Opus 4.5**, the author says the premature-ending behavior was no longer observed in these tasks; the new harness dropped explicit context resets and used Agent SDK automatic compaction in continuous sessions.
- After moving to **Opus 4.6**, the author removed the fixed sprint decomposition, retaining planning and conditional QA. This is an illustrative model-specific ablation, not proof that compaction or task decomposition is universally unnecessary.

### 3. Reported cost and quality boundaries

- In a retro-game-maker example with Opus 4.5, the author reports **20 minutes / $9** for a solo agent and **6 hours / $200** for the full harness. The latter created a broader, 16-feature specification across ten sprints and yielded a more functional interactive application, although it still had UX and physics defects. The costs and outputs are **not workload-equivalent**, so the comparison cannot isolate the causal effect of evaluator, planner or added runtime.
- The author gives concrete evaluator findings: a rectangle fill handler that only affected drag endpoints, an entity-delete selection-state mismatch, and an API route order conflict producing HTTP 422. These are examples of targeted executable QA rather than evidence of comprehensive defect recall.
- In a later browser-based digital audio workstation example with the simplified Opus 4.6 harness, the author reports **3h50m and $124.70** total. The phase accounting is planner $0.46, first build $71.08, first QA $3.24, second build $36.89, second QA $3.09, third build $5.88, third QA $4.06. QA found nonfunctional or stubbed core interactions including clip dragging and audio recording.
- The author explicitly acknowledges residual bugs, evaluator blind spots, lack of human-grade musical assessment and the need to reassess harness components after model upgrades.

All figures above are **vendor-reported case-study observations**; no independent reproduction, source audit or controlled multi-task confidence interval is claimed.

## Inferred — generalizable engineering mechanisms

**Adaptive harness selection.** The marginal value of an evaluator or fixed decomposition depends on the model's baseline competence, task difficulty and quality risk. A platform could route easy tasks through a minimal loop, harder tasks through an independently scored evaluator, and high-risk tasks through protected executable tests plus human approval.

**Contract-based evidence.** A pre-build acceptance contract reduces the chance of post hoc grading against what the generator happened to produce. However, if generator and evaluator can jointly negotiate away difficult requirements, the contract needs an external policy owner or a reviewable approval boundary.

**Separation of concerns.** Planner outputs are proposed scope, generator changes are artifacts, evaluator reports are evidence, and the user/policy authority determines acceptance. Each should have its own identity and revision.

**Recovery as a separate problem.** A multi-hour continuous context does not establish crash safety. Store task/event history, working tree or commit identity, checkpoint and test results outside ephemeral model or worker state. A context reset and a process restart are different failure events.

## Hypotheses and falsifiable experiments — not executed

### Experiment A: harness component ablation across model capability

- **Corpus:** 30 fixed app-development tasks with functional, UX and security acceptance criteria; split into development and locked holdout subsets. Include underspecified tasks and tasks requiring multi-hour work.
- **Arms:** (A) solo; (B) planner + solo; (C) planner + one end-of-run evaluator; (D) planner + per-feature contracts and evaluator; (E) full setup plus periodic context resets. Repeat with at least two model versions and multiple random seeds.
- **Controls:** Fixed repository/task SHAs, API model IDs and effort settings, tool and SDK versions, sandbox image digest, CPU/memory quotas, token/wall-clock limits and evaluator prompt SHA. Freeze test definitions before attempts.
- **Primary metrics:** independently verified functional success, seeded defect recall and false-acceptance rate, successful tasks per $100, p95 time to validated delivery, human review minutes. Secondary: number of QA rounds, scope inflation, context tokens, retry/recovery cost.
- **Falsifier:** If added planner/evaluator/reset stages do not improve quality-adjusted cost at a given model/task stratum, the corresponding scaffolding is not justified. Analyze interaction effects rather than comparing only the best run of each arm.

### Experiment B: evaluator independence and contract gaming

- Construct tasks with intentionally misleading visual polish, stubbed interactions, an inaccessible button, a security defect and contradictory planner-added requirements.
- Compare (1) generator self-review, (2) same-model fresh-context evaluator, (3) evaluator with protected executable oracle and hidden tests, and (4) independent human adjudication.
- Inject a malicious or weakly scoped sprint-contract proposal; require the acceptance authority to reject a contract that silently removes original requirements.
- Measure defect detection by severity, approval calibration, false-positive review cost, specification drift, and correlation of generator/evaluator mistakes.

### Experiment C: long-horizon recovery versus context compaction

- Run tasks with deliberately interrupted model streams, worker crashes, stale handoff files, tool-side effects that succeed without acknowledgments, and sessions exceeding context budgets.
- Compare continuous compaction, fresh-context handoffs and event-log replay with a revision-pinned checkpoint. Preserve tool call IDs and external operation reconciliation keys.
- Measure duplicate side effects, state loss, recovery completeness, p95 restart time, tokens spent reconstructing context, and verified task completion.

## Competing architectures and trade-offs

| Option | Benefit | Failure / cost |
| --- | --- | --- |
| Single agent with tool tests | Minimal orchestration and latency | Self-review bias, scope omissions and long-context drift |
| Planner + single builder | More complete requirements | Planner hallucinations or unauthorized scope expansion |
| Planner + independent QA | More systematic behavioral checks | Extra tokens and time; QA can still approve defects |
| Sprint contracts + per-sprint QA | Fine-grained evidence and earlier failure localization | Contract negotiation overhead, brittleness and grading drift |
| Model-conditional evaluator and reset policy | Spend verification only where needed | Routing misclassification, model-version coupling and harder reproducibility |
| Protected CI oracle + human risk gate | Stronger acceptance provenance | Test maintenance, reviewer attention and slower release |

## Unknown and evidence limitations

- No publicly reproducible, fixed multi-task evaluation dataset, random seeds, raw traces or complete source code of this particular experimental harness were established from the article.
- The author does not disclose evaluator false-negative rates, uncertainty calibration, safety properties of generated tools, exact prompt versions, cost variance or generalization across independent teams.
- The case-study applications differ in scope, model and run budget. Their dollar figures are **not** a clean controlled comparison.
- Browser-based QA does not establish comprehensive accessibility, security, backend correctness, or data integrity.
- The study does not establish a particular crash-safe scheduler, durable checkpoint format, sandbox policy or event-log implementation.

## Conclusion

**Verified:** Anthropic reports that explicit planning, external behavioral QA and sometimes structured sprint contracts improved selected long-running application builds; it also found that newer models made some earlier scaffolding redundant.  
**Inferred:** Harness components should be treated as **versioned, measurable interventions**, not permanent universal requirements.  
**Hypothesis:** Model/task-conditional scaffolding can reduce cost without increasing false acceptance if independent executable acceptance criteria are protected.  
**Unknown:** Whether these gains survive broad, blinded, resource-matched trials or long-term operational failures.

**Next action:** Reproduce Experiment A with protected oracle tests, then compare recovery and evaluator-independence variants before promoting a durable recommendation into the [verification](../../../domains/verification.md) and [evaluation](../../../domains/evaluation.md) domain briefs.
