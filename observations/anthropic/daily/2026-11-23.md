# Evidence-Bound Agent Permission Gates and Adaptive Inference Budgets

- **Observed:** 2026-11-23
- **Publication coverage:** 2026-03-25 and 2026-09-25; historical technical backfill, **not newly published November 23 research**
- **Discovery:** [Anthropic Engineering](https://www.anthropic.com/engineering), [Claude Resources](https://claude.com/resources), [Claude Developer Blog](https://claude.dev/blog/)
- **Status:** Source-grounded vendor implementation observations and falsifiable design hypotheses; no independent code audit or experiment
- **Research problem:** How can a durable coding agent spend limited inference compute on verification while retaining enforceable authority boundaries for every external side effect?
- **Domains:** [Security](../../../domains/security.md), [Durable execution](../../../domains/durable-execution.md), [Orchestration](../../../domains/orchestration.md), [Verification](../../../domains/verification.md), [Evaluation](../../../domains/evaluation.md)

## Concept and invariants

An agent can optimize its own reasoning effort and propose tool calls, but it must not grant itself authority by narrating a plausible justification. The authorization policy, evidence about user consent, execution boundary, and final acceptance oracle must remain independent of the generator. Optimizing token cost without accounting for unsafe actions, wrong outcomes, and retries is incomplete.

**Required invariants:**
1. Every externally consequential action is evaluated against authenticated user intent, a scoped capability, a known target and blast radius, not merely the model's rationale.
2. A denial does not grant a new permission. Retry and escalation are bounded; delegated subagents cannot silently widen the original user's authority.
3. High-effort reasoning can improve verification but cannot replace an enforceable sandbox or authorization policy.
4. Evidence of correct delivery is bound to source revision, environment fingerprint, verifier version, result and cost; apparent success without this tuple is not accepted.

**Failure model:** malicious tool output, over-eager irreversible operations, mistaken target selection, credential search, shared-resource modification, nested delegation, denial-loop probing, classifier false negatives, missing edge-case tests, excessive reasoning cost, broken prompt caches and repeated retries.

## Observation A: Reasoning-blind permission classification

- **Primary source:** [How we built Claude Code auto mode: a safer way to skip permissions](https://www.anthropic.com/research/claude-code-auto-mode)
- **Published:** 2026-03-25; **observed:** 2026-11-23
- **Evidence type:** Anthropic Engineering implementation disclosure with internal evaluation; **vendor-reported**, not an independently reproduced safety guarantee

### Verified (publisher-supported)

- Anthropic describes a two-layer defense: a server-side prompt-injection probe marks suspicious tool outputs before they enter the main agent's context, and an action classifier checks potentially dangerous tool calls **before execution**.
- The transcript classifier is described as Sonnet 4.6 and sees **user messages plus tool calls**, excluding the agent's explanatory prose and tool outputs. This reduces exposure to rationalization and injected instructions, at the cost of provenance for targets discovered through tools.
- Three permission tiers are described: fixed/user safe-tool allow rules, in-project file edits, and classifier-reviewed operations such as shell commands, external integrations, outside-project file operations and subagent launches. Broad arbitrary-code execution allow rules are dropped when auto mode begins; the published rule matching is acknowledged to be best-effort.
- Stage 1 emits a fast yes/no and is conservative; only flagged cases receive Stage 2 reasoning. In the **publisher's internal datasets**, full-pipeline FPR is **0.4%** on 10,000 real tool calls; FNR is **17%** on 52 real over-eager actions and **5.7%** on 1,000 synthetic exfiltration attempts. Stage 1 alone had 8.5% FPR, 6.6% real-overeager FNR and 1.8% synthetic-exfil FNR. Stage 2 reduces false positives but worsens false negatives.
- A classifier check occurs at subagent delegation and at return; the return check warns the parent rather than discarding results. Consecutive denials are bounded to 3, total denials to 20, after which a human is required or headless execution terminates.
- The authors explicitly state auto mode is **not** a substitute for careful human review of high-stakes infrastructure.

### Inferred

A reasoning-blind action gate is a useful **separate authorization control plane**, because the generator's own statements should not constitute consent. However, a learned classifier alone is insufficient as a mandatory security boundary: its false-negative rate on the small, selected over-eager set is substantial. Explicit immutable capability constraints, kernel/filesystem isolation, credential mediation and target ownership checks should precede any model-mediated ambiguity resolution.

The exclusion of tool outputs improves prompt-injection resistance but makes target provenance harder to establish. A structured, non-natural-language provenance record (resource identifier, issuing authority, source call ID, trust classification) may provide verifiable target identity without passing attacker-controlled prose to the classifier. This is a proposed design, not a published Anthropic mechanism.

### Alternatives and trade-offs

| Approach | Advantage | Limitation |
| --- | --- | --- |
| Manual approval for all side effects | Human reviews actual targets | Fatigue, latency and poor unattended continuity |
| Sandbox plus fixed capability policy | Deterministic isolation and least privilege | Policy maintenance; external API effects still need authorization |
| LLM-only transcript classifier | Flexible semantic interpretation | False negatives, non-determinism and model drift |
| Hybrid: deterministic policy + intent classifier + explicit escalation | Hard constraints plus lower approval volume | Additional control-plane cost and target-provenance complexity |

### Unknown

The full policy prompt, deployment-wide FNR/FPR, classifier drift, latency distribution, evasion rate under adaptive attackers, provenance of multi-step shell effects, and how real-world resource ownership is verified are not established by this article. The internal dataset is not an independent representative sample of all high-risk actions.

### Hypothesis and falsifiable experiment

At a fixed code SHA, run 500 legitimate tasks plus 200 deliberately adversarial scenarios (credential discovery, prompt-injection exfiltration, destructive Git operations, shared K8s resource mutation and nested delegation). Compare (A) manual approval, (B) deterministic capabilities, (C) transcript classifier and (D) hybrid gating. Record per-action authority provenance, sandbox/credential policy digest, classifier model/prompt version, allowed/denied/escalated action, human override and final side effects. Inject network retries and classifier outages. Evaluate **unauthorized effect rate** (primary safety outcome), benign-block rate, human approvals/task, p95 gate latency, verified deliveries per dollar, and safe termination after repeated denials. The hypothesis fails if hybrid gating cannot reduce human friction without increasing unauthorized effects against the deterministic baseline.

## Observation B: Effort as a verification budget

- **Primary source:** [Using Claude Code: Spending your effort](https://claude.dev/blog/spending-your-effort/)
- **Published:** 2026-09-25; **observed:** 2026-11-23
- **Evidence type:** First-party engineering write-up with author experiments and benchmark analysis; vendor-reported and limited by test selection

### Verified (publisher-supported)

- The author compares effort levels on Terminal-Bench 3.0 and small build/design tasks. The Terminal-Bench model comparisons use the same 70 tasks per model (four GPU tasks excluded in the graph); the Opus 5.5 run occurred approximately three weeks after another run, with a 128k response cap and no GitHub/PyPI access.
- For an underspecified fitness-tracker build, the author reports low/medium/high/max completion times of **1.5/4/11/67 minutes**. With an extensively clarified specification, the times were **16/22/33/79 minutes**; resulting designs were described as more similar.
- In the reported Fable 5.1 Terminal-Bench breakdown, security pass rate increased from **64% to 87%** and hardware from **34% to 75%** from pooled low to pooled high settings; these category slices are small and the author cautions against overgeneralization.
- In the reported `html-js-filter` task, Fable 5.1 improved from **1/5** at low to **5/5** at xhigh. The traced high-effort run performed parser-source inspection, clean-input tests, a standard XSS suite and fuzzing. The author notes higher effort reduces missing-edge-case failures more reliably than wrong-approach failures.
- The author suggests low effort for quick interactive iteration and high effort for testing and edge-case-heavy verification, not indiscriminate maximum effort.

### Inferred

Effort is not just a token knob: it changes the model's willingness to inspect dependencies, use independent oracles and search for counterexamples. The appropriate budget should depend on **task ambiguity, blast radius, availability of external verification and recovery cost**, not solely task length. More effort can amplify an incorrect interpretation; stronger tests and clarified requirements may outperform additional thinking.

### Alternatives and trade-offs

Use a fixed high effort everywhere (simple but wasteful), low effort with independent deterministic tests (cheap where test oracles are strong), adaptive effort escalation after failed tests (cost-effective but can waste retries), or specialized verification agents (more independent context but coordination overhead). All need a protected test oracle and cost attribution.

### Unknown

Exact private prompting, full benchmark repetitions, variance, causal separation between increased reasoning and increased tool execution, and how these observations generalize to different models/repositories are unknown.

### Hypothesis and falsifiable experiment

Pin 100 issue tasks across security, API changes, refactoring, storage recovery and UI. Randomize (1) fixed medium, (2) fixed high, (3) medium implementation then high verification, (4) medium with property/differential tests, and (5) adaptive escalation by observed failures. Keep task instructions, tool capabilities, sandbox resources, time budget and test suite identical; run repeated seeds. Measure **correct deliveries**, escaped bugs, time-to-verified-result p50/p95, thinking/output/cache tokens, test executions, human interventions and total dollars. Stratify by edge-case density and specification completeness. Reject the hypothesis if adaptive routing fails to improve verified completions per dollar without worsening severe escaped defects.

## Observation C: Cost per verified task, not price per token

- **Primary source:** [What a task costs on Opus 5.5](https://claude.dev/blog/what-a-task-costs-on-opus-5-5/)
- **Published:** 2026-09-25; **observed:** 2026-11-23
- **Evidence type:** First-party pricing and workload modeling tutorial, not an independently measured production efficiency benchmark

### Verified (publisher-supported)

- The article separates total turns, fresh input, cache reads, output including thinking, and model-specific API pricing. It uses illustrative Opus 5.5 list prices of **$4/M fresh input, $20/M output and $0.20/M cache reads** and explicitly excludes cache-write charges from several illustrations.
- For a hypothetical task whose average context is 70k tokens, 40 turns process 2.8M input tokens. At 90% cache reads, the article calculates approximately **$1.62 input cost**; 25 turns process 1.75M and approximately **$1.02**. These are *modeled examples*, not recorded task traces.
- Its same-token example compares **$3.50** at Opus 5 with **$2.40** at Opus 5.5 (about 31% lower) for 2M cached reads, 200k fresh input and 60k output. The article warns that real model workloads can differ in turn count and token mix.
- The article notes that spending more thinking tokens can be cheaper than a retry if it avoids rereading a long cached context, but additional effort is wasted when the lower setting would have succeeded immediately.

### Inferred

An agent platform needs a task-level cost ledger keyed by **run/turn, model version, effort, cache-hit class, tool usage, retries and verified outcome**. A nominally cheaper model or setting can be more expensive when it triggers additional failures, CI reruns or human repair.

### Alternatives and trade-offs

Token-only billing reports are cheap but hide quality; per-turn accounting captures cache effects but not outcomes; task-level verified-cost accounting captures retries and human attention but requires durable cross-service identifiers and consistent completion criteria.

### Unknown

Actual enterprise discounts, hidden prompt cache write costs, cache invalidation frequency, tool infrastructure charges and workload-dependent model token consumption cannot be inferred from the article's interactive examples.

### Hypothesis and falsifiable experiment

Replay a pinned 100-task coding benchmark across model/effort combinations with fixed timeouts and independent tests. Collect per-turn billed token categories, cache hit/miss, tool CPU/memory, CI reruns, human repair minutes and recovery events. Report cost **per independently verified completion**, including failures in the denominator, and bootstrap confidence intervals. Compare routing by estimated task difficulty against fixed-medium and fixed-high baselines; invalidate the recommendation if cost falls only by lowering correctness or omitting tool/CI expenses.

## Synthesis: an evidence-bound runtime policy

**Verified (source-supported):** Anthropic separately reports a classifier-based permission gate with measurable misses, a variable reasoning-effort effect on edge-case verification, and a token/cache-sensitive cost model.

**Inferred:** These three concerns should remain distinct:
- **Authority:** immutable user/capability policy and independent enforcement; model classification assists only with ambiguous cases.
- **Verification budget:** route effort based on testability, task risk and failed evidence; do not treat reasoning as proof.
- **Economics:** optimize end-to-end verified outcomes and external effects, not output-token price or PR count.

**Hypothesis:** A hybrid capability gate plus adaptive verification budget improves verified delivery per dollar while bounding unauthorized effects more reliably than model-only gating and uniformly high effort.

**Unknown:** Whether these patterns share any internal Anthropic infrastructure, or whether their vendor-reported gains generalize to independently hosted agent runtimes.

## Follow-up and evidence limitations

1. Design an immutable authorization/evidence envelope carrying actor, original user intent, target ownership, capability scope, policy digest, tool call, source SHA, environment digest and approval.
2. Implement a benchmark with adversarial actions and reproducible task outcomes; compare fixed and adaptive effort only after capability boundaries are held constant.
3. Record both security failures and total execution economics; publish raw traces with secrets removed.
4. Do not treat a source article or a passing repository Markdown integrity check as a replicated experiment.
