## 1. Engineering problems and system boundaries

When agent-generated changes increase, three surrounding systems need more
capacity and stronger correctness guarantees:

1. **Review as a scarce-attention control plane.** Detection, adjudication,
   risk-based approvals and rollback must be evaluated together, not simply
   counted as AI review findings.
2. **Runtime observability as an evidence plane.** Model/tool steps, costs,
   versions and outcomes need correlatable telemetry, without assuming a trace
   proves task correctness or external side-effect atomicity.
3. **Continuous security verification as a stateful lifecycle.** Findings
   must remain tied to code revisions, threat context, triage decisions and
   subsequent fixes across a changing repository.

These issues should be studied under existing [verification](../../../domains/verification.md),
[evaluation](../../../domains/evaluation.md),
[security](../../../domains/security.md), and
[delivery](../../../domains/delivery.md) domains.

## 2. First-party implementation evidence

### A. Risk-tiered review, convergence and human attention

- **Original:** [How the Claude Code team does code review](https://claude.dev/blog/solving-code-review-at-anthropic/)
- **Published by the original engineering blog:** 2026-10-15.
  **Discovery hub listing:** 2026-10-16. The source and listing dates differ;
  this note uses the article's own publication date.
- **Class:** First-party engineering account. Measurements below are
  author-reported, not independently reproduced.

**Verified (publisher-reported):**

- The team layers self-verification and fresh-context agent review before
  a PR, AI code/security review on PRs, conventional tests/build checks,
  risk-based human approval, merge queue validation and staged release.
- Human review is risk-tiered: the authors describe no required human
  approver for eligible low-risk changes, one for medium-risk changes, and
  two for high-risk changes; some sensitive paths always require humans.
  Machine review does not count as a human approval.
- An approval is associated with a specific commit; unverified additional
  changes can invalidate it. Reviewer feedback loops use incidents/reverts
  as evaluations, and re-review has a round cap plus diff-only follow-ups.
- From June to September, the team reports more than doubling merged PRs
  while the share later reverted fell by over 40%. This is a vendor-reported
  team statistic, not a causal attribution to any isolated mechanism.

**Inferred architecture implication:** Review effort should be allocated by
change risk and evidence completeness rather than identical blocking gates
for every diff. Reviewer quality needs both recall and *convergence*
measures; an agent repeatedly "fixing" low-value feedback can increase
overall delivery cost.

**Alternatives / trade-offs:** Uniform human approval is easier to audit but
becomes a throughput bottleneck. Fully automated approval reduces queue time
but amplifies classifier error. A risk-tiered hybrid requires trustworthy
path ownership, source-SHA binding, falsifiable risk classification and
rollback evidence.

**Unknown:** Exact classifier thresholds, reviewer model prompts, false-negative
rates and reproducible costs; the post does not disclose enough to rebuild its
internal review service.

**Hypothesis / experiment:** Replay a fixed suite of incident-inducing and
clean PRs across full review vs. risk-tiered review. Measure seeded-defect
recall, false-positive rate, review rounds to convergence, human wait P95,
total human minutes and reverted/escaped defects per verified delivery.

### B. Agent traceability and observability contracts

- **Original:** [Agent observability on the Claude Platform](https://claude.com/resources/articles/agent-observability-on-the-claude-platform)
- **Published:** 2026-10-14.
- **Class:** First-party product/technical announcement, not an exposed
  implementation of the telemetry backend.

**Verified (publisher-reported):**

- The Claude Platform now offers OpenTelemetry export from Managed Agents,
  the Messages API and Claude SDKs, with spans for agent turns, model
  calls and tool use and metadata such as latency, token usage and IDs.
- The article says traces follow OpenTelemetry GenAI semantic conventions
  and can be delivered to compatible OTLP backends.
- The feature is described as a public beta. Availability and completeness
  must be checked against the product documentation for each deployment.

**Inferred architecture implication:** A common tracing and identity layer can
make agent failures, latency and costs comparable across runtimes, but only
when a run, tool call, sandbox, commit SHA and validation outcome can be
joined without ambiguous identifiers. Tracing a call does not prove that an
external action occurred exactly once.

**Alternatives / trade-offs:** Provider-native tracing improves setup but
may have gaps at external tool/worker boundaries. Application-owned
OpenTelemetry spans provide more control but need disciplined propagation
and cardinality/privacy policies.

**Unknown:** Span sampling behavior, propagation across externally hosted
MCP servers, whether incomplete/lost tool results are distinguishable,
retention defaults and cross-provider semantic equivalence.

**Hypothesis / experiment:** Instrument a reproducible agent run across an
LLM gateway, tool runner, sandbox and async task queue; inject retries,
lost acknowledgments and worker restarts. Measure end-to-end trace join
rate, missing spans, duplicate external operations, P95 export lag, cost
attribution error and privacy leakage.

### C. Revision-aware continuous security findings

- **Original:** [Claude Security now scans continuously and tracks fixes](https://claude.com/resources/articles/claude-security-now-scans-continuously-and-tracks-fixes)
- **Published:** 2026-10-21.
- **Class:** First-party product announcement. Not an implementation audit.

**Verified (publisher-reported):**

- Claude Security supports a deep baseline repository scan followed by
  recurring change-sensitive scans based on risk and complexity; customers
  can scope branches and repositories and attach deployment/security
  context and reviewed threat models.
- Findings can be marked fixed when a code change addresses them and
  reopened if subsequently detected again. The service describes
  cross-repository vulnerability analysis, API/webhooks, an MCP connector
  and role-based project permissions.
- The announcement says the feature is in public beta for Enterprise
  customers. Its cited vulnerability counts are vendor-reported figures,
  not independently verified detection precision or recall.

**Inferred architecture implication:** A security finding is a *versioned
state machine*, not a static comment on a diff. It needs finding identity,
affected source revision, threat-context version, remediation revision,
recheck policy, triage provenance and reopening semantics.

**Alternatives / trade-offs:** Scheduled whole-repository scans maximize
breadth but are costly and stale between runs. Pure diff scans are efficient
but can miss changed reachability, dependencies and threat assumptions.
A baseline plus incremental scan with periodic full control cases can
bound these risks if the invalidation rules are sound.

**Unknown:** Internal reachability algorithm, risk scoring calibration,
cross-repo dependency resolution, false-negative rates and the evidence
used to auto-close a finding.

**Hypothesis / experiment:** Construct a fixed vulnerability corpus across
two services. Compare full scans against risk-based incremental scans under
dependency changes, security-policy updates and deliberate regressions.
Measure detection recall, false closure/reopen rates, freshness lag, total
compute, reviewer minutes and time to verified fix.

## 3. Synthesis and next action

The common engineering bottleneck is now **evidence lifecycle and attention
allocation**: which revision was examined, by what rule, how the result
changes when code/context changes, and who must act when automation is
uncertain. The convergence story in review, trace identity in observability,
and finding state in security are related but not interchangeable.

This intake should lead to concept-based updates only after testing the
hypotheses above. It does **not** establish Anthropic's private internal
implementation details, nor does it imply that these features share a common
backend architecture.
